## Questions

1. What is “thin controller, fat service” in one example from your code?
2. What edge cases did you handle for list pagination?

---

## Answers

1. Controller handles HTTP codes only and the heavy business logic stays in services.

In my Task API, TaskController only extract the query params and call the service. TaskService will do all the logic (check DB, compare, filter) and then TaskController will return the status code eg. 200, 400, 401.

2. Page or limit received is not integer eg. 'abc'. Requires ValidationPipe + @IsInt to return invalid type error 400 Bad Request.

Limit is large eg. 100, which kills the performance by large amount of records. ValidationPipe + @Max(50) to prevent large number for limit.

### Reviewer comments

- **Q1:** Good core split: controller = HTTP transport, service = business logic. Naming `TasksController` → `TasksService` on list/filter is a valid thin-controller example. **Polish:** cite a **fatter** service method from your Task API — e.g. `updateTaskStatus` loads the task, throws `NotFoundException` if missing, updates, saves. That shows business rules in the service better than `getTasks`, which mostly delegates to the repository. Also: Nest sets status codes from return values and thrown exceptions (`NotFoundException` → 404); the controller usually doesn't manually pick 400/401 — 401 is auth, not tasks.
- **Q2:** Solid boundary validation: non-integer `page`/`limit` → `@IsInt()` + `ValidationPipe` → 400; oversized `limit` → `@Max(50)` cap. **Deepen:** add defaults when omitted (`page=1`, `limit=10`), reject zero/negatives (`@Min(1)`), and page past the end → empty array (not 404). Tie to a concrete DTO/route (e.g. `GET /notes?page=&limit=`) so it's clearly *your* list endpoint. See [NestJS validation](https://docs.nestjs.com/techniques/validation).
